# SMAIRT AI Skill Usage

The skills under `src/smairt/assets/skills/` are SMAIRT-owned procedures for
coding assistants: thin instructions that call the `smairt` CLI to do the
mechanics. They ship as package data inside `smairt` itself (alongside
`assets/scaffold-blueprint.yaml`) and are resolved from an installed package
by `smairt.skills`, never by a path relative to the repo checkout. The
project-level contract — the two unit kinds, frontmatter duties, evidence
rules, and the stakes/explanation rules — lives in each project's own
`AGENTS.md`, generated by `smairt new`. Skills reference that contract; they
don't restate it.

## Available Skills

- `smairt-new-project` — interview a researcher and scaffold a new
  project, fully-flagged.
- `smairt-orient` — join or resume a session from derived state.
- `smairt-new-question` — start an exploratory probe.
- `smairt-new-stage` — add a step to the spine.
- `smairt-close-question` — record what happened, what it means,
  and a verdict.
- `smairt-fork` — record alternatives, contained or propagating.
- `smairt-adopt` — walk a pre-existing project's folders after
  `smairt adopt` and propose reference units, one approval at a time.
- `smairt-adversarial-review` — researcher-invoked, argues against
  the current interpretation from the units' own evidence. The only skill of
  the eight that must never fire on its own; `smairt connect` enforces that
  wherever the harness offers a mechanism to (see "Delivery" below).

Each is a folder containing a single `SKILL.md`; `smairt.skills.list_skills()`
lists the names above and `smairt.skills.read_skill(name)` returns one's text.

## Delivery

`smairt connect <harness>` installs all eight skills into that harness's own
project-local skills surface, alongside the hooks it already writes — the
same command, the same never-overwrite-a-researcher's-edit policy. Two
targets cover all six supported harnesses:

- `.claude/skills/<name>/SKILL.md` — Claude Code.
- `.agents/skills/<name>/SKILL.md` — Codex, Cursor, OpenCode, Gemini CLI, pi.

They're copied, not referenced: no harness has a project-local "also read
skills from this path" setting, and a reference would resolve to a per-venv
install path that breaks for the second person who clones the project. Each
installed `SKILL.md` carries a comment naming the "delete this directory and
re-run `smairt connect`" remedy for when a `smairt` upgrade makes the copy go
stale. Re-running `smairt connect` for a second harness that shares
`.agents/skills/` with an already-connected one is a no-op — the files are
already there, byte-identical.

## Use

Install SMAIRT, create the project, and connect a harness:

```bash
uv tool install .
smairt new
smairt connect claude-code   # or codex, cursor, opencode, gemini-cli, pi
```

The assistant then discovers the skills on its own — nothing further to run.
It should read the project's own `AGENTS.md` and `STATUS.md`, and follow
whichever skill matches the task at hand — never reconstruct project state
from conversation memory alone.

Skills do not create projects, replace the CLI, or validate scientific
claims; the researcher owns novelty, judgment, and conclusions.
