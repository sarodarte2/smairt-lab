# The cross-harness contract

Type: grilling
Status: resolved
Blocked by: 08, 10

## Question

How do harness-specific adapters (CLAUDE.md, AGENTS.md, OpenCode, Gemini, skills) derive from the canonical SMAIRT contract so no harness invents its own conventions? Decide the derivation mechanism (generated? symlinked? checked?) and, critically, the enforcement boundary: what `smairt check` can actually verify versus what can only be communicated. An instruction in CLAUDE.md is not an invariant.

## Answer (consolidated — settled by the harness survey plus decisions made on the guidance-surfaces and state-contract tickets)

SMAIRT owns the contract; harnesses get thin, generated wiring:

- **Prose contract:** one canonical repo-root `AGENTS.md`, read natively by Codex/OpenCode/Cursor, via one setting by Gemini CLI, via a generated 2-line `@AGENTS.md` bridge by Claude Code. Bridges are generated by `smairt`, never hand-maintained.
- **Procedures:** SMAIRT-owned skills, shipped with the tool (see [Consolidating the guidance surfaces](08-consolidating-the-guidance-surfaces.md)); all supported harnesses assumed skill-capable.
- **Enforcement boundary:** what `smairt check` verifies (frontmatter schema, statuses, drift, structure) is enforced — via each harness's blocking/stop hook, installed by SMAIRT when the researcher selects a harness, with CI as the harness-independent floor. Everything else is communication and is deliberately kept minimal.
- No harness ever defines a SMAIRT convention; a new harness is supported by writing one bridge + one hook config template.
